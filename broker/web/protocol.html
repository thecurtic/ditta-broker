How DITTA works

DITTA is an open protocol for federated web search. Independent operators index what they know best and answer queries against it, free or for a payment over Lightning, with no central party in between.

Version 0 is a draft. It is unstable, and later revisions can break anything built against it.

The problem

Indexing is expensive, and nobody pays the people who do it. Someone who knows a niche can build a better index of it than a general engine can, but there is no way to be paid for answering queries against it, and no way for searchers to find it.

Two roles

  • An indexer keeps a corpus of documents, answers queries against it, and publishes a signed announcement: where it can be reached, what its corpus looks like, and what a query costs.
  • A broker takes a query, decides which indexers to ask, pays them, merges what comes back and returns the results. What a broker sells is judgment: which indexers to ask, and how to combine their answers.
  • A node can be both. There is no registry and no privileged node. Nodes learn about each other from announcements, which any node can pass on to its peers, unchanged: any change would break the signature. Roles are declared by the node itself; only experience checks them.

This site is a broker. What it shows is one broker's view of the network, not the network itself.

How a query flows

  1. A query reaches a broker

    You send a query to a broker. How you reach a broker is not part of the protocol; a search page like this one is one way, a program is another.

  2. The broker picks indexers

    It reads the announcements it holds, and the per-term statistics it can ask each indexer for, and decides whom to ask. How it decides is its own business.

  3. A charging indexer asks to be paid

    It answers with HTTP 402 and a signed payment challenge carrying a Lightning invoice. An indexer that charges nothing just answers.

  4. The broker pays and asks again

    It pays the invoice and sends the identical query again, with proof of payment in the request header. The query's bytes do not change.

  5. The indexer answers

    It searches and returns a result set: documents in its own order of relevance, best first.

  6. The broker merges and ranks

    It merges the result sets from every indexer it asked, ranks them by its own judgment, and returns one list.

Payment uses L402, an existing convention for paying for HTTP requests over Lightning. DITTA adds no payment mechanism of its own; it adds a signature on the payment challenge, so a broker knows the invoice comes from the indexer it chose. Paying is optional: an indexer can charge nothing.

What holds it together

Identity is a key
Every node has a keypair, and its messages are signed with BIP-340 Schnorr signatures. The key is a node's lasting identity: its endpoint can change, its key does not, so whatever reputation it earns attaches to the key. TLS encrypts the connection but never says who anyone is.
One message, one byte sequence
Every message has a single canonical serialization, so implementations in different languages produce and check identical signatures. Published test vectors prove it, byte for byte.
Strict by default
Every message, the announcement included, is rejected for a missing field, a wrong type or a bad signature. Every message except the announcement is also rejected for a field it doesn't define: these operational messages are strict because some of them move money, so a misspelled field fails loudly. Announcements tolerate unknown fields at their top level only, so the protocol can grow.
Indexers can be stateless
An indexer commits to a price, gets paid, then searches. It holds nothing between issuing a payment challenge and seeing it redeemed. After that it keeps very little: a mark that a single-query credential is spent or, under a batch credential, the request identifiers it has already served, so a retried query is never counted twice. Both are dropped when the credential expires.

What the protocol leaves alone

How to index. How to rank. How a broker chooses indexers. How a node finds its first peer. What happens when a paid indexer returns nothing. These are where operators compete, or set their own policy.

Version 0 also gives you no way to check that a broker returned what its indexers actually sent: once results are merged, nothing proves where each one came from. If you don't trust a broker, your remedy is a different broker.

Build against it

  • The specification: protocol.md in ditta-protocol/ditta-spec, with its change log.
  • The test vectors, in the same repository: valid and invalid messages with their canonical bytes, hashes and signatures, for checking an implementation byte for byte.
  • ditta-protocol/ditta-wire-py: a Python implementation of the wire format, useful as a reference for serialization and signatures.
  • This broker is an independent implementation, built from the specification and the test vectors alone. It is not the reference implementation.
  • To search the network from a program rather than implement the protocol, use this broker's client API.
  • Running an indexer isn't covered here yet; the specification is the starting point.
