# Search and Indexer Selection — Broker Feature Spec

**Status:** implemented (front-end redesign, October 2026). Where this spec and the code disagree, raise it.
**Scope:** broker back end, web front end, and agent-facing API. Not part of the DITTA wire protocol.

This spec defines how search behaves on the broker: the search flow, optional indexer selection, refresh, spend, Tor exclusion, every loading and failure state, and the agent-facing API. How things look is defined in `DESIGN.md`; this spec defines what they do.

If this spec contradicts `DESIGN.md`, another spec, or a task prompt, don't silently follow either one. Flag the conflict and ask which is intended.

---

## 1. What this change delivers

1. **Visual refresh.** Bring the existing front end in line with `DESIGN.md`: tokens, typography, figures, card and results appearance, writing, accessibility.
2. **Indexer selection.** Searchers can optionally narrow a search to one or more indexers, from the web UI or the API.
3. **Search behaviour.** The search, refresh, spend, Tor and state behaviour below, applied to all searches, scoped or not.
4. **Agent-facing API.** The same selection and behaviour exposed to agents, through the same back-end code path as the web UI.
5. **Protocol explainer page.** A page explaining how the DITTA protocol works, specified separately in `explainer-page.md`.

## 2. Principles

1. **Full network is the front door.** The default search uses the broker's full judgment across every indexer. Narrowing is opt-in.
2. **Selection constrains the set; the broker still decides.** A searcher may narrow which indexers are asked. Within that set, the broker alone routes, ranks and merges. Searchers never control ranking or weighting.
3. **The pubkey is the identity.** Every selection, stored search and API call refers to indexers by pubkey. (The URL itself carries only an opaque id; the pubkeys live in client storage under it — see 4.3.) Names are display labels pulled from the pubkey's current state and are never used to resolve anything.
4. **State is always visible.** If the next search is scoped, the searcher can see that wherever they type.
5. **Never widen silently.** If a requested scope can't be honoured, say so. Never fall back to the full network on the searcher's behalf.
6. **Money is never a surprise.** Any search that can spend sats shows the cost before it runs, and the actual spend after.
7. **Nothing moves under the reader.** Results on screen don't reorder while being read.

## 3. Relation to the indexer naming spec

The indexer naming spec states that the searcher never controls routing and cannot select, filter, exclude or pin indexers. **This spec replaces that rule** with principle 2 above: searchers may constrain the set of indexers asked; they may not influence routing, ranking or merging within it. Update the naming spec's hard rule and non-goals to match.

Everything else in the naming spec stands: names and descriptions are generated by the broker, keyed to pubkeys, and never enter a DITTA message.

## 4. Web UI behaviour

### 4.1 Selecting indexers

- Each indexer card has a "Search this" checkbox. Searchers can tick one or several.
- Ticking a card immediately adds that indexer as a chip in the search bar. Unticking removes it.
- Nothing ticked means a full-network search.
- Unreachable indexers can't be ticked; the checkbox is disabled with the reason shown.
- Only indexers the broker currently lists can be selected. There is no free-text or endpoint entry.
- When an indexer charges, its price is shown beside its checkbox.

### 4.2 The scope in the search bar

- The current scope is always shown as chips in or beside the search input: one chip per selected indexer, showing its current name.
- Each chip has an X that removes that indexer from the **next** search. With two or more chips, "Clear all" removes them all.
- Removing chips does not change the URL or the results on screen. It only shapes the next submitted search.
- When the next search is scoped, a line under the bar reads "Searching 2 of 5 indexers". When it isn't, no line.
- On a results page from a scoped search, the chips remain in the bar, so the searcher can see that their next search is still scoped.

### 4.3 Submitting, URL and refresh

- Submitting a search is the only action that queries indexers or spends sats.
- On submit, the URL updates to an **opaque search id** (`?r=<id>`), not the query. The query is never placed in the URL: it would leak to server and proxy access logs, browser history, the address bar and shared links. The id maps, in this browser's local storage, to the executed search — its query and its selected pubkeys (none for full network).
- The URL always describes the last executed search, never unsubmitted edits.
- Executed searches and their results are stored **client-side only** (this browser's local storage), keyed by the opaque id. The broker keeps no searcher-facing log of searches or results. Refreshing a results page re-displays the stored results for that id. It queries no indexer and spends no sats.
- Sharing a results URL is not a goal. If one is opened in a browser that has no stored search for that id (a different device, cleared storage), the page finds nothing and offers to run the search. It never re-queries or spends on its own.

### 4.4 Results

- One ranked list, best first, regardless of source. The broker alone decides order.
- Every result shows which indexer it came from (current name; tapping it opens that indexer's card).
- A "Group by indexer" toggle shows the same results grouped by source. It is a view, not a filter, and doesn't change order within groups beyond what the broker set.
- The **route map** (which indexers were asked and which contributed to the shown results) is retained from the current front end. This spec earlier omitted it by oversight; it stays, restyled to `DESIGN.md`. Its placement on the results page is decided during the build.

### 4.5 Spend

- Before submitting, if the scope includes paid indexers, show the broker's **cost estimate** under the bar ("About 2 sats"), scoped to the selected indexers. This is the same quote the broker already computes, not a separately derived maximum.
- After a search, the results header shows the sats actually spent.
- The spend cap is enforced by the back end, not only the UI. If a search would exceed it, the back end returns an over-cap error naming the indexers involved; the UI surfaces that before or on submit.

### 4.6 Tor exclusion

- The "Exclude Tor indexers" option stays and applies to every search.
- If it removes some selected indexers, name them under the bar before submitting.
- If it removes all selected indexers, disable "Search" and show: "All selected indexers use Tor. Untick 'Exclude Tor indexers' or choose other indexers."
- Never widen to the full network to compensate.

### 4.7 Recent searches

- A "Recent searches" collapsible lists past searches: query, scope, result count, sats spent, age, with "Open" and "Delete" per entry and "Clear all".
- "Open" re-displays the stored results; it doesn't re-run the search.
- Stored only in this browser, and the collapsible says so.

## 5. Flows

### 5.1 Full-network search

1. Searcher types a query and submits.
2. URL updates to the executed search.
3. Progress line: "Asking 3 indexers…". After 3s it adds "Some are slow to answer." Indexers are not named as they respond: the broker answers once, with one ranked list, so nothing reorders while the person reads (live progress is a possible future feature).
4. Results render as one ranked list once ranked.
5. Nothing arrives after the list is shown, so nothing can reorder it.

### 5.2 Scoped search

1. Searcher ticks "Search this" on one or more cards. Chips appear in the bar.
2. Cost and Tor notices update under the bar if relevant.
3. Searcher submits. Only selected indexers are queried; the broker ranks within that set.
4. The URL updates to a new opaque id (`?r=`); the query and the selected pubkeys are stored under it in this browser (4.3).
5. Chips stay in the bar on the results page.

### 5.3 Widening after a scoped search

1. On a scoped results page, searcher removes chips with X or "Clear all". Results and URL don't change.
2. Searcher submits. The new search runs on the remaining scope, or the full network if none remain. URL updates.

### 5.4 Refresh

1. Searcher refreshes any results page.
2. The stored results for the URL's search are shown again. No indexer is queried; nothing is spent.

## 6. States

| State | Behaviour |
|---|---|
| Loading | Progress line: "Asking N indexers…". No spinners over content, no skeleton shimmer. |
| Slow indexer | After 3s without the answer, the line adds "Some are slow to answer." It can't name which: the page hears from the broker once, when every asked indexer has answered or failed (decision 5). |
| Partial results | Results header reads "Results from 2 of 3 indexers" and names each indexer that failed. |
| No results | Sieve or Query figure, "No results for '[query]'", one action: "Search the full network" when scoped, otherwise "Try different words". |
| Indexer unreachable | Card stays visible with status "unreachable"; its checkbox is disabled with the reason. |
| Selected indexer became unreachable | Its chip shows it as unreachable; the search runs on the rest and says which was skipped. If none remain, block the search and say why. |
| Empty network | Plug figure, "No indexers are reachable right now", one action: "Try again". |
| Over spend cap | Explained before submit (4.5). |
| Error | Say what happened and what to do. Never "Something went wrong". |

## 7. Back end

Web UI and agent API share one code path for search.

- The search endpoint takes an optional list of pubkeys. Absent or empty means full network. The exclude-Tor option and spend cap are parameters of the same call.
- Accept only pubkeys the broker currently lists. Unknown or delisted pubkeys return an error naming each one. Never drop them silently.
- Selection constrains the routing set only. Routing, ranking and merging within the set are unchanged.
- If the effective scope is empty (after Tor exclusion, or every selected indexer unreachable), return an error. Never widen.
- The response includes:
  - the effective scope: pubkeys actually queried, and selected pubkeys skipped, each with its reason;
  - the indexer pubkey on every result;
  - sats spent.
- The back end stores no searcher-facing log of searches or results. Re-display without re-querying is a client-side concern: the web UI keeps executed searches and their results in this browser's local storage under the opaque id (4.3). The back end still learns per indexer from each query — keyed only to the indexer pubkey, never to a searcher — which is a separate concern from search re-display.
- The spend cap is enforced here, identically for UI and API.

As shipped (`broker/server.py`, tested in `tests/test_scope.py`):

- `POST /client/search` and `GET /client/quote` take `pubkeys` (a JSON list; on the quote, comma-separated). Malformed → `bad_request`.
- Every search response carries `scope: {selected, queried, failed, skipped: [{pubkey, reason}]}` and `charged_msat`. `skipped` lists only selected pubkeys; reasons are `excluded` (Tor), `unreachable`, `never_contacted`, `budget`, `pay_disabled`, `no_pricing`, `fanout`, `low_score`. The quote carries the same `scope`, as a prediction.
- Errors: `unknown_pubkey` with `pubkeys[]`; `empty_scope` with `skipped[]`; `unsatisfiable` with the `pubkeys[]` its price rests on. A scope error is returned before any invoice is minted.
- Selection filters the candidate set before rank, as Tor exclusion and reachability do. Fanout still applies within a scope (reason `fanout`).

## 8. Agent-facing API

- **Search:** the endpoint in section 7, with the same parameters and errors as the web UI.
- **Network listing:** returns, per indexer: pubkey, current name, "Covers" description, stats (documents, terms, languages, last ingest), price, transport (including whether it's Tor), reachability. This is enough for an agent to choose a scope on purpose. As shipped: `GET /client/peers`, with `name`, `covers`, `searchable` and, when false, `unsearchable_reason` beside the existing corpus, pricing, transport and `reach` fields. `GET /` documents all of it.
- **Errors are explicit and machine-readable:** unknown pubkey, empty scope, over spend cap, each naming the pubkeys involved.
- **Docs** tell agents to store and send pubkeys, not names. Names drift and are display labels only.
- Agents have no chips, drafts or refresh. Every call is explicit and self-contained.
- **MCP:** when the operator enables it, the MCP server offers the same search to agents as tools (`search`, `redeem`, `quote`, `list_indexers`), with `indexers` as the scope by pubkey. It is a client of this API like the web UI, so scope, errors and never-widen behave identically. A paid search returns the invoice, its amount and the end of its settlement window; the agent pays with its own wallet and redeems with the preimage. `GET /` names the MCP URL when it is enabled.

## 9. Non-goals

- Any searcher control over routing, ranking, weighting or merging within the selected set.
- Selecting indexers by name or by endpoint.
- Remembering a selection across visits beyond the URL of an executed search.
- Any change to the DITTA wire protocol.

## 10. Acceptance criteria

1. A search with nothing ticked queries the full network.
2. Ticking two cards shows two chips; submitting queries only those two; the response's effective scope lists exactly those pubkeys.
3. Removing a chip on a results page changes neither the URL nor the results shown.
4. Refreshing a results page makes no indexer requests and spends no sats.
5. An unknown pubkey in an API call returns an error naming it.
6. A scope emptied by Tor exclusion blocks the search in the UI and errors in the API; neither widens to the full network.
7. A paid scope shows the broker's cost estimate before submit and the actual spend after; a scope that would exceed the spend cap errors from the back end, naming the indexers involved.
8. Renaming an indexer doesn't change which indexer a stored search or URL refers to.
9. Late results never reorder a list already on screen. (Holds by construction: the broker answers once, with one list.)
10. Every state in section 6 has been triggered and checked (mock slow and unreachable indexers as needed).
11. The front end passes the visual review in `DESIGN.md` section 11.
